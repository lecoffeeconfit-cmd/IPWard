# IPward

IPward is a local-first privacy activity utility built with Expo SDK 57, React Native, TypeScript, and Expo Router. It has a clearly labelled sample preview plus a device workspace that accepts authorized evidence. The app never presents sample events as activity from the user's phone.

## Run

```sh
npm install
npm run web
```

For iOS and Android, run `npm run ios` or `npm run android` in a configured native development environment. A **new Android development build** is needed for the bundled Usage Access module; Expo Go cannot load custom native code. The module does not grant itself permission. In Settings, the user opens Android Usage Access settings and explicitly enables IPward. Returning to the app or tapping Refresh reads the OS daily foreground-time totals. A native Android build has not yet been compiled on this machine.

## What works with actual user data

- **Apple App Privacy Report import:** On iPhone or iPad, enable App Privacy Report in Settings → Privacy & Security. Use its Share action to save the `.ndjson` report, then choose it in IPward Settings. IPward parses domain-contact summaries and sensor access intervals on-device. It keeps the report's source and provenance, rejects unrelated or oversized files, skips invalid records, and deduplicates repeated imports by app and domain. The latest imported aggregate replaces an overlapping one.
- **Historical report snapshots:** Save all imported records or focus on one reported app. Compare two snapshots of the same source. Snapshots are explicitly labelled historical, never live captures.
- **Android app use:** With user-granted Usage Access in a custom development build, IPward reads daily foreground-time aggregates from Android `UsageStatsManager` and shows them in Activity and Apps. This does not reveal in-app content, messages, calls, or network traffic. Android may aggregate usage into calendar-day buckets.
- **Local storage:** On iOS and Android, imported normalized events and profile labels use a versioned SQLite store with indexed timestamps and retention pruning. The web preview uses a bounded AsyncStorage fallback. Preferences, demo rules, and saved reports use app-local storage. There is no cloud activity backend. The database is not encrypted by IPward; device storage protections apply.
- **Export:** JSON and CSV include provenance and leave unavailable transfer bytes blank. Native builds can also create a readable PDF activity summary. A native share sheet or web download starts only after an explicit action. Native export files are stored temporarily in app cache; Settings can clear them, and Clear history clears them with imported observations.
- **Security Center:** Open it from Protect to review loaded network evidence, exact matches against a user-imported STIX2 file, local domain-list matches, and carefully labelled event-level behavior clues such as first-seen destinations, large background transfers, unusual DNS shapes, and repeated contact cadence. It shows a dated finding timeline, persistent guided device and account checks, a forensic handoff, and a JSON report with explicit export confirmation. Duplicate large-transfer notices are collapsed by app, destination, and day. Its check count is evidence coverage, not a device safety score. Indicator files stay in local app storage and are not independently verified. The Phone speed section runs a short in-app JavaScript timing check, keeps up to twelve local results, and compares calm-condition release-build runs in the same app installation. Results can be cleared and the latest is included in the security report.
- **Internet & devices:** Open connection diagnostics from Connections or Security Center. The page reports the current connection type when available and runs a user-started internet test against Cloudflare. It shows response time, variation, approximate download and upload speeds, an animated progress indicator, and up to twelve locally saved results. Quick uses about 350 KB and standard about 3 MB of test payload, plus protocol overhead. Users can stop a test or clear its history. The latest result is included in the optional security report. Adding `expo-network` may require a new development build for the connection-type display; the internet test itself also works when the native module is unavailable.

## Product experience

Five primary tabs, responsive navigation, dark/light mode, reduced motion, evidence labels, Overview, Activity, Apps, Connections, Protect, sensor and communication views, destinations, notices, trust center, search, filters, demo captures, local report comparison, retention, and settings are implemented. The Overview includes a seven-day privacy digest. Imported domains first encountered by IPward are listed as new to local history, with copy that makes clear this does not mean the app recently started using them. Apple-supplied owner labels take priority; a small local domain-suffix directory adds estimated company and category hints for some common providers, while unknown domains remain unclassified. Domain details include Ask IPward, a local, rule-based explanation grounded in the selected record; there is no connected AI service. The Alerts view now compares event-level local history with each app's prior seven observed days and calls out first-seen domains or unusually high destination/upload counts. Imported Apple report aggregates are excluded from daily baselines. Protect supports local Allow, Block, Alert, and Ignore rules for exact domains, IPv4 addresses/ranges, ASNs, and country codes, with more-specific rules taking precedence. These rules only evaluate records already loaded in the app and do not change network traffic. Users can optionally import a domain or hosts file for exact, on-device reputation-list matches; IPward labels these as matches from the user's file, without claiming its source or threat type is verified. No observed domain is sent to an external reputation service. The visual system uses sculpted instrument panels, an animated count dial, an animated outbound trace, and spring-press controls. The dial's motion is decorative; its center number is the reported count. In Sample preview, all events and classifications are fictional fixtures. Demo protection rules only simulate outcomes.

The **Privacy Map** organizes supported evidence into an app → data access → recipient → possible-purpose graph and always distinguishes observed network traffic, data an app could collect, declarations that are not yet connected in this build, and fields found in a user-selected account export. JSON, NDJSON, and CSV account exports are inventoried locally: IPward saves category totals and representative field paths but discards raw values. The same workspace includes exposure-review scores (not safety or security scores), per-app review priorities, and links to official account-data request and deletion instructions. Account deletion is never automated.

The **Web Privacy** workspace performs an on-device review of a URL the user pastes. It checks transport and URL-shape clues, removes common tracking parameters for a sanitized copy, compares the host with locally loaded lists and bundled provider hints, and can prepare local alert or block-preview rules. It is not a live reputation lookup, browser history reader, Safari content blocker, or guarantee that a site is safe.

Protect also includes **Standard, Privacy, Strict Privacy, and High-Risk Protection profiles**. Profiles apply an understandable group of IPward settings and locally evaluated category-preview rules without deleting unrelated user-created rules. Rules can now target provider organizations and destination categories and may expire after one hour, one day, or one week. These controls remain previews until a separately authorized native network provider exists.

The **Data & ads** view combines imported sensor access intervals and domain contacts into an app-filtered timeline and a per-app data journey. It separates resource access, destination contacts, and possible cross-app ad signals instead of implying one caused another. It shows each sensor interval's start and end, and the first and latest contact times (when supplied) plus aggregate count for each Apple domain row. Intermediate contact times are unavailable. For an Apple-flagged domain, it can show a low-confidence timing clue if the same app accessed a resource within 15 minutes of that domain's latest contact. This is a temporal comparison, not an estimate of speech, payload, ad placement, or cause. Apple's flag supports only possible cross-app profiling, not proof of a particular ad use. Potential cross-app collection flags and report-supplied domain owners are shown with their limits. Users can add timestamped, local notes about ads they personally saw, including the app and wording or topic, and remove those notes later. These notes are self-reported, included in JSON export, and cleared with history; they are never presented as automatically detected ads. Users can review category-specific steps for revoking an app's permission and changing tracking or ad preferences. On Android, a compatible development build can open an observed Android app's system settings; IPward cannot change another app's permission itself. Apple report apps must be controlled on the originating Apple device. A new native build is needed after adding `expo-intent-launcher`.

The app-focused source panel identifies microphone and other resource access, browser text as unavailable, and network contacts as a separate modality. It shows up to ten recent source records without treating them as detected words. An ad note may optionally include up to ten words or topics the user remembers saying or typing; these are displayed as local, self-reported notes and never as verified microphone capture or marketing transfers.

## Limits that remain

IPward does **not** yet include a live device-wide network VPN/Network Extension provider, per-app packet attribution, transfer-byte accounting from real traffic, actual tracker enforcement, device-wide background network history, cross-app sensor monitoring, calls/SMS access, notification listening, or an email OAuth integration. Apple report imports do not expose bytes, IP addresses, server geography, foreground state, or payloads; those fields remain unavailable in the UI. A first-seen notice means IPward encountered the app/domain pair in a new import, not that the app recently added the connection. Provider hints are a small offline directory, not an authoritative or frequently updated tracker list. Ask IPward is a local rules-based explainer rather than an AI model and cannot establish a connection's purpose. Android Usage Access provides time aggregates only. The current-IP display is transient and is not added to history. Device and network checklists are self-reported review aids, not OS attestation. Account-export inventory accepts individual local files rather than full archive traversal and never reads or stores the values it inventories. IPward cannot read spoken or typed words from other apps, identify which ad appeared or its receiving app, prove why an ad was selected, or directly revoke another app's permissions. Exact message counts and ad causation are not inferred.

The Security Center does not yet attest device integrity, inspect installed apps or privileged permissions, detect VPN/profile/certificate changes, check patch level, run a live threat feed, or analyze forensic backups and logs. An absent indicator match does not mean a device is clean. A genuine deep forensic scan needs a separately built, consensual desktop workflow; native iOS/Android checks need the relevant platform authorization and development work.
Its timing check measures IPward's own JavaScript scheduling and a small calculation while the app is open. It cannot measure other apps, identify a process causing slowness, estimate Pegasus likelihood, or detect spyware from performance alone. Temperature, battery health, power-saving settings, storage pressure, updates and other ordinary factors can affect results. Browser and development-build runs are shown for inspection but do not establish a phone baseline.
Connection diagnostics measures the internet path to Cloudflare, not the negotiated Wi-Fi radio speed or total cellular-plan usage. Cloudflare can see the device's public IP address during the test. Bluetooth-tethered internet may appear as a network route on Android; testing direct transfer speed to headphones or another accessory requires a compatible paired device and is not implemented.

The Android native module is source-complete and autolinked, but still needs an Android development build and device validation before release. iOS App Privacy Report import is implemented in JavaScript and builds for iOS, but has not been exercised on a physical iPhone in this environment. No App Store or Play Store release, security audit, production privacy policy, or native network-entitlement review has been completed. This is a substantial product foundation, **not yet a production-ready device-wide monitor**. See [docs/platform-capabilities.md](docs/platform-capabilities.md).

## Checks

```sh
npm run typecheck
npm run lint
npm test
npx expo export --platform all
npx expo-doctor
```

Tests cover Apple report parsing, provenance, deduplication, snapshot validation, classification boundaries, capability gating, range filters, estimation guards, capture comparison, CSV safety, and persistence validation. The browser Settings screen and app navigation have been inspected in the local preview.

`expo-doctor` also uses online Expo and React Native Directory metadata checks. If those hosts are unreachable, its offline checks can pass while those two checks remain unverified.
